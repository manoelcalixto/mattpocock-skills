# Adopt versioned planning context for Codex session boundaries

The upstream workflow treats the planning conversation as the primary source through `grill-with-docs`, `to-spec`, and `to-tickets`, then starts implementation in fresh sessions. That leaves material decisions vulnerable to flattening or loss when Codex cannot consume the original conversation. `CONTEXT.md` preserves vocabulary and ADRs preserve exceptional architectural choices, but neither records the ordinary planning decisions that specifications, tickets, implementation, and verification must cover.

This fork adopts a versioned **Planning context** for multi-session work. A model-invoked `planning-context` skill will own a per-effort **Decision ledger**, downstream coverage, Git **Planning checkpoints**, and consumer validation. New repositories will receive `docs/agents/planning.md` from `setup-matt-pocock-skills`; existing repositories will receive the default configuration on first use. The default ledger path is `docs/planning/<effort>/decision-ledger.md`.

Ledger entries use per-effort IDs such as `DEC-001`. The agent proposes and records decisions whose change would alter downstream behavior, constraints, scope, contracts, test seams, or architecture. Routine implementation choices stay out. Each entry has concise decision and rationale fields, validity separate from delivery coverage, and phase-specific coverage obligations. Once checkpointed, its decision and rationale are immutable. A changed decision is a new entry that supersedes the old one, while coverage and evidence may be appended. An ADR remains canonical when a decision warrants one; the ledger points to it instead of duplicating its rationale.

`grill-with-docs` and `wayfinder` produce entries. `to-spec` maps active IDs to their consequences, and `to-tickets` maps them to applicable tickets. Specifications and tickets repeat only the consequences needed to act, while the ledger remains canonical for rationale. `implement` and `implement-spec` validate any declared Planning context before work begins. Legacy specifications and tickets that declare no Planning context remain valid. If implementation cannot honor an active decision, it stops and returns to planning for a superseding entry and a new checkpoint. Concurrent implementers record evidence in their tickets or commits; the final coordinator aggregates verification coverage in the ledger after merging their work.

A Planning checkpoint is required before every fresh session. It creates an exact-file commit on the effort branch, without staging unrelated work, and uses phase-specific gates: an intermediate checkpoint may leave future destinations pending, the final planning checkpoint requires applicable specification and ticket coverage, and implementation completion requires applicable verification evidence. Consumer branches and worktrees must descend from the exact checkpoint SHA. External specifications and tickets receive a Planning context block with the ledger path and SHA after the commit; local artifacts resolve the checkpoint through a Git trailer. The branch is pushed only when a remote consumer, pull request, or separate clone requires it. Planned knowledge reaches the shared base with the implementation that makes it current, unless it already records current truth.

This deliberately trades a new artifact, stricter validation, and additional commits for durable reasoning and reproducible session boundaries. We reject conversation summaries as the canonical bridge because they are lossy, a single project-wide ledger because it creates unrelated conflicts, and immediate merge of planning commits because proposed knowledge would appear to be current shared truth before its implementation exists.
